## 一、告警引擎与时序（15 题）

### Q1 一条规则监控 100 台主机，怎么保证只产生"该产生"的告警？

**一句话**：用**指纹**（fingerprint）当事件主键——`MD5(rule_id | 排序后的labels | severity | query)`。
一台主机一个 labels（含 host/metric），所以一条规则天然产生 100 个互不干扰的指纹；
同一指纹反复触发只更新同一个事件，不会刷屏。

**深入**：labels 必须排序后再拼，否则字段顺序不同会被算成两条；`query` 里带上
scope/算法/表达式，所以**改阈值或换算法 = 换指纹 = 新事件**，老事件走恢复。
这套指纹算法来自夜莺 `alert/process/process.go:797`。

**别这么说**："用告警去重"——面试官会追问去重键是什么，答不出就露馅。
👉 `app/engine/state.py: fingerprint()`

### Q2 为什么用"活跃表 + 历史表"两张表？

**一句话**：`alert_cur_events` 存**当前状态**（一指纹一行，恢复即删），`alert_his_events`
存**追加账本**（首次触发/发了通知/恢复各写一行）。查询"现在有哪些告警"打小表，
审计"这个告警怎么变的"读账本。

**深入**：账本不是每轮都写——100 台主机 × 15s 每轮写 100 行，一天就是几十万行无意义数据。
所以我们只在**有意义的状态变化**时追加（`is_new or notified or is_recovered`）。
这是"双表"设计里最容易被忽略的取舍。

**别这么说**："历史表就是备份"——历史表是账本（append-only），不是备份。
👉 `app/engine/core.py: _persist()`

### Q3 平台重启，活跃告警会丢吗？会不会误报"已恢复"？

**一句话**：不丢也不误报。worker 启动时从 `alert_cur_events` **回放**该规则的活跃事件进状态机
（`_replay`），所以重启后这些指纹仍在"fires"里，不会因为"这一轮没数据"被判恢复。

**深入**：回放重建的 `FireState` 会带上 `notify_cur_number`，通知计数**续算**
（不是从 1 开始），避免重启后重复轰炸。验收测试：`test_d2_engine.py::test_restart_replay`。

**别这么说**："重启会丢，所以要持久化队列"——我们不用持久化队列，用回放更轻。
👉 `app/engine/core.py: RuleWorker._replay()`

### Q4 规则改了要重启才能生效吗？

**一句话**：不用。**对账式调度**每 9s 把"期望的 worker 集"和"现有的 worker 集"做 diff：
新增规则起 worker、删除规则停 worker、关键字段（expr/severity/算法/窗口/Prom 数据源）变了就重建。

**深入**：选择"对账"而不是"每条规则一个 cron job"的原因是：① 规则 CRUD 只影响相关 worker；
② 坏规则不会污染别的规则；③ 不需要为每条规则维护调度表达式（间隔或 cron 由 worker 自己算下次时间）。
自检端点 `GET /api/ops/dev/engine-state` 能看到对账心跳和每个 worker 的 `alive/fires`。

**别这么说**："我用了 Celery/APScheduler 定时扫全表"——扫全表 vs diff worker 集，
规模上去后差别很大。👉 `app/engine/core.py: reconcile()`

### Q5 事件进队列时为什么要 deepcopy？

**一句话**：因为状态机后续会**原地改写**同一个 event 对象。如果队列里放的是引用，
下一轮评估把 `trigger_value` 改掉、或把它改成"恢复事件"，消费端拿到的历史就全乱了。

**深入**：这是夜莺源码注释里明确写过的坑（"队列内对象被后续评估原地改写"）。
Python 里 `copy.deepcopy(ev)` 一样必须。
👉 `app/engine/state.py: process()` 里的 `out.append(copy.deepcopy(ev))`

### Q6 告警骚扰怎么解决？

**一句话**：三个参数 + 一个留观：
`notify_repeat_step_min`（0=只发一次，N=每 N 分钟重发）、`notify_max_number`（封顶）、
`notify_recovered`（恢复是否通知）、`recover_duration_s`（指标回落要持续多久才算真恢复）。
每条发送都写 `notification_records` 台账，"为什么没收到"可查。

**深入**：**这里我踩过一个很隐蔽的 bug**：重复通知的判定在消费端（`should_notify`），
而状态机早期对"同指纹更新"只改内存状态、**不入队** → 消费端永远收不到更新 →
"repeat_step 到时重发"在真实链路里从未发生。单元测试只测了那个纯函数，所以一直是绿的。
后来把更新事件也入队（标记 `is_update`），并补了链路级测试。
**这个坑的价值**：告诉我"函数被测试"不等于"链路被测试"。

**别这么说**："加重试次数"——重试与重发是两件事。
👉 `app/services/notify.py: should_notify()`

### Q7 两级静默的差别？为什么 MutedAll 还要删状态机指纹？

**一句话**：`mute_type=0`（MutedAll）= 事件根本不产生；`=1`（NotifyOnly）= 事件照常落库、
只是不发通知。MutedAll 必须**额外把指纹从状态机里摘掉**——否则它一直停在 fires 里，
静默解除后永远走"更新"分支，再也不会重新触发。

**深入**：这是夜莺同款语义（静默期事件不落库，静默结束的下一轮评估重新产生事件）。
周期时段（如每日 02:00-03:00 备份窗口）+ TagFilter（`==/!=/=~/in`）都支持。

**别这么说**："静默就是不发通知"——那只说对了一半。
👉 `app/engine/core.py: consume_one()` 的 `if m == 0:` 分支

### Q8 阈值检测和自适应检测怎么选？

**一句话**：有明确阈值的**可用性**指标用 threshold（磁盘水位、CPU 打满、探活失败）；
平稳基线上的尖峰/阶跃用 3σ；无分布假设的多维离群用 IsolationForest。
3σ 严格要求窗口内 ≥5 个点且 σ≠0，否则**直接返回空**——不硬凑结论。

**深入**：三种算法共用同一条"异常点 → 指纹 → 事件"管线，指纹里带算法名，
所以换算法 = 新事件，老事件按恢复处理。演示时同一条曲线配两条规则对比触发时机，
能把"静态阈值 vs 自适应"讲得很直观。
👉 `app/engine/detect.py`

### Q9 threshold 语义上有个反直觉的地方，你注意过吗？

**一句话**：threshold 是对**窗口内每个点**独立判定，所以窗口里只要有一个点超阈，规则就会告警。
想要"持续超阈才告警"要用 `for_duration_s`；想排除单点毛刺要把 `window_s` 调小（1-2 个采集周期）。

**深入**：这个语义直接影响了我们的测试写法——要触发规则，必须让窗口内**所有点**都超阈，
或者清空环形窗口只留一个超阈点。第一版测试就是在这里反复"莫名其妙不触发"。
👉 教程《04-异常检测与规则调优》§2

### Q10 数据只存内存不会丢吗？为什么不全落库？

**一句话**：原始明细只进**内存环形缓冲**（默认 2h），落库只存 1m/5m **聚合**
（`metric_agg`，默认 7d）。查询接口对调用方透明：明细窗口走内存，超窗自动走聚合。

**深入**：动机是 2C4G 单机也要跑得动——100 台主机 × 15s × 多指标的原始点写库，
单机磁盘和写放大都吃不消。代价是"诊断时最早的点已不可取证"，
所以我们在报告里强制写 `not_checked`（"环形缓冲仅保留 5 分钟，告警窗口已无法取证"）——
**把能力边界写进报告，而不是编一个原因**。

**别这么说**："内存快"——面试官想问的是"为什么敢不落库"，答案是配额与成本的权衡 + 诚实的边界声明。
👉 `app/store/ring.py`、教程《05-AI 诊断 Agent 拆解》§2

### Q11 为什么用 SeekDB？踩了什么坑？

**一句话**：选它是因为 MySQL 协议兼容 + 内置向量检索（案例召回直接用）+ Apache-2.0 可捆绑 +
单机 1C2G 能跑。踩的坑有四个：① 官方镜像入口把参数当 **SQL** 执行后退出（不能传 command）；
② 索引反射不可用（`BLOCK_SIZE` 语法）→ 索引**手写**且关掉 alembic 的索引比对；
③ **VECTOR 列让 ORM 反射崩** → 该表走 raw SQL 并在 env.py 里跳过反射；
④ **ENUM 列做索引首列 + 等值过滤** 抛 `(1210, Invalid argument)` → 索引首列改 INT（我们通过
"全库 25 个 ENUM 列审计，只有这一处失败"定位的）。

**深入**：第 4 个坑的定位过程值得讲：先排除数据/权限/大小写，再横向对比"唯一带索引的 ENUM 列
（位于复合索引第 3 位）正常"，最后删索引验证 → 结论是"ENUM 作索引首列 + 等值过滤"。
这是可复现的、有对照组的排查。
👉 `backend/migrations/versions/13bddd4dad5e_*`、`04-数据库设计说明书.md` §7/§10/§12

### Q12 时间显示成负数（"-27896 秒前"）是什么问题？

**一句话**：数据库会话时区与应用的 UTC 不一致——SeekDB 的 `NOW()` 返回服务器本地时间（UTC+8），
而我们 `datetime.utcnow()` 是 UTC。修法是连接串带 `init_command="SET time_zone='+00:00'"`，
并把历史脏数据按偏移修回。

**深入**：这类 bug 的特点是"功能都正常，只有时间戳错"，很容易被当成前端问题查很久。

### Q13 告警流为什么用 SSE 不用 WebSocket？

**一句话**：告警是**单向**推送，SSE 更轻（HTTP 长连接、自动重连、不用额外协议），
且能复用现有的鉴权与反向代理。诊断过程的"思考流"同样用 SSE。

**深入**：SSE 有两个坑我处理了：① `EventSource` 不能带 header → 用**一次性 ticket**
（`/api/sse-ticket`，消费即焚，断线重连要重新换票）；② ChatOps 要 POST 消息体 →
不能用 EventSource，改用 `fetch` 读流自己切帧。
👉 `app/services/sse_ticket.py`、`static/js/api.js`

### Q14 事件队列积压会导致什么？怎么发现？

**一句话**：会导致**通知延迟**——而告警产品的核心承诺就是"出事主动报"，延迟就是失效。
发现靠自检端点：`GET /api/ops/dev/engine-state` 里的 `event_queue_size`。

**深入**：我们实测真的积压过 **1793 条**，SSE 推送几分钟才到。根因是消费端
`await` 了真调 LLM 的告警摘要（数秒/条），100 台主机同时触发时消费者被 LLM 串行拖住。
**恰好在最需要通知的风暴场景**。修复：摘要丢后台任务（并发上限 2）+ 队深 >50 时放弃摘要让路。
压测前后：SSE 延迟从"分钟级"变成 **9.8s**（门槛 15s）。
👉 `app/engine/core.py: _spawn_ai_summary()`、教程《12-运维与排障手册》§4

### Q15 你会怎么给告警系统做压测？

**一句话**：不是"看日志估"，而是① 用真实上报协议注册 100 台主机并灌数据；
② **直接调同一批评估函数**（`reconcile` + `worker._eval_once`）计时，得到评估周期 P50/P95；
③ 用真实 SSE 端点 + 真实规则测端到端推送延迟；④ API 采样 30 次取 P95；⑤ 跑完**自清理**。

**深入**：跑完自清理这件事很重要——我们第一版没清事件表，留下了 100 条**幽灵告警**
（指向已删除主机的 active 事件）挂在大盘上。后来加了"孤儿事件清理"脚本，
并写进运维手册（`repair_demo_data.py --purge-orphans`）。
实测数据：评估周期 P95 ~100ms、大盘 P95 ~5ms、SSE ~10s、上报 ~470 次/s。
👉 `backend/scripts/bench_100_hosts.py`

## 二、AI Agent 与 LLM 工程（15 题）

### Q16 你的 AI 诊断 Agent 是什么架构？

**一句话**：**单 Agent ReAct 循环 + 终态工具**。收集上下文 → 循环里让模型选工具（8 个只读工具）
→ 工具结果回灌 → 最后必须调用 `write_findings` 产出结构化报告。

**深入**：为什么不上多 Agent（triage/dispatch/synthesis）？调研过 Aurora 的多 Agent 编排，
结论是 V1 单 Agent 足够，多 Agent 的收益（并行、角色隔离）在"单机 100 主机"规模上不明显，
成本（上下文管理、结论综合、调试难度）却立刻上来。所以编排器留 feature flag，V1 不启。
这属于**有意识的范围控制**，不是做不到。

**别这么说**："我用了 LangChain/LangGraph"——面试官会问"你自己实现了什么"，
框架本身不是亮点，编排与约束才是。

### Q17 LLM 凭什么不乱编根因？

**一句话**：四道防线：① 工具面**只读且能力有限**，拿不到数据就返回 `NO_DATA` + 原因
（"V1 不读远程日志"），模型没有编造素材；② 提示词里写死证据纪律（结论必须能指到具体工具输出、
不确定要用"可能"、查不出就直说不知道）；③ 工具结果**结构化**（status/data/note），
`NO_DATA` 不能被当成成功数据；④ 报告里的引用可点击回放原始输出，用户能自己验证。

**深入**：报告用**强 schema** 校验：YAML frontmatter 七字段 + 四个必填 H2 + 结论三档
（CONFIRMED/LIKELY/INCONCLUSIVE）+ 影响面四分类（Affected / Checked healthy /
Changed other reason / Not checked），且 **Affected 每条必须带 evidence_token**——
"引不出证据的不配进受影响组"。校验失败带错误清单重试 ≤2 次，再失败写 `failed` stub。
实测：面对"主机未纳管 + 数据窗口已过期"的场景，它会给 `INCONCLUSIVE` 并说明缺什么数据，
而不是编一个根因。

**别这么说**："加了温度 0 就不乱编了"——温度只影响发散度，不解决事实性。
👉 `app/services/findings.py`、`prompts.py`

### Q18 模型无限调工具怎么办？

**一句话**：预算五件套：① `max_steps`（默认 30）；② **最后一轮撤走所有工具只留 `write_findings`**
（逼出结论）；③ 同参数重复调用直接拒绝（`name + sorted(params)` 做键）；④ 单工具输出超限落盘，
只给路径 + 限量预览；⑤ 历史超阈值用快模型压缩（压缩后仍记住曾导致溢出的调用，继续拒绝重复）。
外加循环护栏：同工具连续 3 次空/错注入转向提示，5 次强制收尾。

**深入**：这套是 HolmesGPT 生产验证过的做法，我们照抄了机制。另有单次调用超时 180s、
整轮 deadline 900s——到点写 stub，不无限等。
👉 `app/services/rca.py`

### Q19 诊断过程怎么做到实时可见？

**一句话**：三层留痕 + SSE 流。SSE 事件：`session_start / thinking / tool_call / tool_result /
tool_denied / hint / validate_retry / token_count / content / done`；
落库三层：`incident_thoughts`（思考流）、`execution_steps`（工具瀑布：名字/入参/出参/耗时/状态）、
`rca_findings.tool_call_history`（完整调用史）。前端实时渲染"正在想什么 + 工具瀑布"，
完成后可**完整回放**。

**深入**：还有一个细节：诊断行是**预写**的（`status=running` 先落库），
所以前端立刻能出"调查中"卡片，不用等结果——这个设计学自 Aurora。

### Q20 报告格式为什么要"强 schema"，那不是限制了模型吗？

**一句话**：因为报告要**被人和系统同时消费**——人要读证据与推理，系统要拿它生成变更单。
强 schema 是"可校验"的前提；没有 schema，"合规"就只能靠肉眼。约束换来的是可自动化。

**深入**：另外我们做了"机械性错位的归一化"：模型偶发把 status/confidence 写串、
用中文写强度、把 citations 混在正文里——这些会被归一化而不是判失败，只有**语义问题**才让它重来。
这是"严格但别把模型逼死"的平衡。

### Q21 你的 Agent 有 8 个工具，怎么让模型选对？

**一句话**：靠工具 description + 技能索引 + 提示词纪律。description 里必须写清
"能拿到什么、拿不到时返回什么"；技能索引只注入一行/技能（渐进披露），
模型认为匹配时才 `load_skill` 拉全文。

**深入**：主机参数这块我们踩过坑：ident 是 32 位指纹哈希，而人/AI 说的都是主机名，
早期工具只认 ident → 用户问"mock-db-01 的 CPU"会返回"主机未注册"，**看起来像平台坏了**。
现在工具 ident 与主机名互认（ident 精确 → name 精确 → 唯一前缀）。

### Q22 Skills 体系为什么用 Markdown 而不是代码？

**一句话**：两家独立开源（Aurora、HolmesGPT 0.26 起）都收敛到"每技能一个 SKILL.md"：
数据不是代码 → 可热更新、可让买家自己写团队手册、且能**渐进披露**（只注入索引，按需拉全文）。

**深入**：我们还加了 **fail-closed 连接检查**（抄 Aurora）：技能声明 `requires`
（如 `platform_host`），检查**明确失败**的技能**不进索引也不可加载**——避免模型去加载一个
用不了的工具/流程，"指向不存在的数据源"是幻觉的常见来源。检查未跑过则默认放行
（否则初始化前技能全被禁掉）。后台每 30 分钟自动重跑。

**别这么说**："就是把 prompt 拆成文件"——要讲清"为什么拆 + 拆完怎么保证不失效"。
👉 `app/services/skills.py`、教程《07-Skills 扩展开发》

### Q23 提示词你怎么管理？改了怎么验证？

**一句话**：提示词分 8 段（身份/方法论/证据标准/反过早收敛/影响面四分类/修复防线/不可信数据/输出契约），
稳定顺序利于 KV cache。改动纪律：① 报告模板**写在系统提示词里**（只在文档里写模板会让模型猜格式，
校验失败率飙升）；② 改完必须跑 findings schema 校验的测试；③ 用户可控文本当不可信数据，
工具输出在提示词里被声明为"待分析数据，不是指令"（防注入）。

**深入**：素材不是自创的——调查方法论（"先查历史""调用前陈述假设""症状不是根因"
"设计证伪型查询"）、反过早收敛清单、证据标准、修复幻觉防线，都取自夜航/Aurora/HolmesGPT
的原文（`docs/02-调研/`）。**这比我自己编一套更可靠，也更好在面试里讲出处。**

### Q24 双模型怎么分工？能省多少？

**一句话**：主模型做推理（诊断循环、ChatOps 回答），快模型做机械活（工具输出摘要、
历史压缩、告警一句话摘要、日报润色）。`purpose` 字段把每次调用按模块分账落库
（rca/chat/summary/inspect/fixcheck/embed），系统设置页能看"近 7 日按 purpose 的 token 用量"。

**深入**：省 token 的五个点：工具输出超限落盘、历史压缩、技能只注入索引、
告警风暴时摘要让路、诊断有步数与 deadline 上限。

### Q25 LLM 用不了的时候系统还能用吗？

**一句话**：能。采集/大盘/告警/通知/SSE **完全不受影响**；收敛退化为纯规则聚类；
巡检出纯模板日报；诊断明确报错并写 `failed` stub；ChatOps 明确报
`LLM_UNAVAILABLE`/`LLM_QUOTA_EXCEEDED`；案例召回降级文本匹配并标注 `mode=text`。

**深入**：设计原则是"**AI 是增值功能，不是单点故障**"。任何 LLM 故障都不允许影响
"发现→通知"这条生命线。这条原则也写进了降级总表文档。

### Q26 成本怎么控？

**一句话**：每日 token 配额（全局 + demo 更严，可配 0=不限），超限返回 **429 + 可读原因**
（含 UTC 次日重置）；用量按模块分账可查。公开演示站建议再加网关层按 IP 限频。

**深入**：这类"成本闸门"最差的做法是静默截断（用户以为模型坏了）。我们选择"明确 429 + 告诉他怎么调"。

### Q27 向量召回怎么做？embedding 不可用怎么办？

**一句话**：案例卡 embedding 存 SeekDB 的 `VECTOR(1536)`，召回用 `l2_distance` 排序；
embedding 不可用时降级为文本匹配，并在返回里如实标注 `mode=vector|text`。

**深入**：踩过两个坑：① 某家模型的 `/v1/embeddings` **不是 OpenAI 兼容**
（请求是 `{texts,type}`、响应是 `{vectors}`），网关必须兼容两种形状；
② 我们早期设计成"向量失败即**永久**降级"→ 一次网络抖动就让这个进程此后所有案例都不带向量。
改成**冷却 5 分钟再重试**。而且"永久降级"那次的日志里异常消息是**空字符串**
（`InvalidTag` 的 str 为空），等于什么都没记——所以现在日志一律带异常类型名。

### Q28 你怎么评估"AI 诊断到底准不准"？

**一句话**：不做"准确率"这种没有 ground truth 的数字（**宣传红线也不允许**），
改成可验证的结构性指标：① 报告 schema 合规率；② 结论档位分布（多少 CONFIRMED/LIKELY/INCONCLUSIVE）；
③ 引用可回放率（citations 是否都指向真实执行过的 step）；④ 人工抽检"证据是否支持结论"。

**深入**：我们刻意保留"INCONCLUSIVE 是合法结论"这个设计——把'不知道'当成一种诚实输出，
比强行给个错根因对运维更安全。面试时这句很容易加分。

## 三、工程化与架构（10 题）

### Q29 前后端权限一致性你怎么保证？

**一句话**：**服务端能力集是唯一来源**。新增 `GET /api/auth/perms` 返回
`{read,diag,alert_ops,write,chat}`，前端导航与按钮可见性**一律由它驱动**，
禁止在页面里按 role 硬编码。

**深入**：为什么改这么彻底？因为真实事故就是这么来的——演示账号点进"AI 助手"，
页面热情地邀请提问，然后每个问题都 403（后端门禁是 diag 级，demo 没权限），
而错误信封当时是 FastAPI 默认的 `{"detail":...}`，前端只读 `msg` →
界面只显示"请求失败：HTTP 403"，用户完全不知道发生了什么。
一次修复覆盖三层：权限口径统一到服务端、错误信封统一成 `{code,msg,data}`、
前端按能力集收敏（无权时给明确说明而不是输入框）。

**别这么说**："前端隐藏按钮 + 后端也校验"——这只是防御，没解决"口径两处维护"的根因。
👉 `app/core/security.py: capabilities()`

### Q30 怎么防止"加了接口忘了加测试"？

**一句话**：`tests/test_d8_api_matrix.py` 有**路由覆盖守卫**：从 OpenAPI 契约里列出所有路由，
凡是没有登记在测试矩阵里的 → 测试**直接失败**。矩阵同时对每条路由断言
4 种身份（匿名/demo/member/admin）的期望状态码、错误信封形状、以及"任何路由不得 5xx"。

**深入**：这个守卫真的抓到东西——我加了 4 个新接口后忘了登记，测试立刻红。
另外它抓出过：重名返回 500（应为 409）、错误信封不统一、18 处"资源不存在"返回 HTTP 200、
member 的告警操作被误挡（与设计文档的权限矩阵不符）。

### Q31 错误处理怎么做才算"交付级"？

**一句话**：统一信封 + 分级：
① 所有 4xx/5xx 都是 `{code,msg,data}` 且 `msg` 是**人话**（前端只读它）；
② 可预期的用户输入问题必须降级为 4xx——重名 `IntegrityError → 409`、
字段超限/枚举不匹配 `DataError → 400`（而不是 500 + 把 SQL 堆栈打进日志）；
③ 未预期异常兜底成 JSON（不把 HTML 堆栈丢给前端），同时记完整堆栈。

**深入**：反例就是我们的真实起点——重名建渠道 → `(1062, Duplicate entry)` → **500**，
界面上只有"HTTP 500"。修完之后用户在界面上直接看到"同名资源已存在，请换个名称"。

### Q32 越权被拒绝要不要审计？

**一句话**：要，而且是安全事件里最重要的一类。我们一开始的 `audit(db=None, ...)` 在拒绝路径上
**直接 return**（注释写的是"不阻塞主流程"），结果"拒绝也留痕"这条需求实际从未生效。
改成自建短会话落库（失败只告警不抛），并加断言测试。

**深入**：面试里这类"看起来实现了、其实没生效"的例子很有说服力——
它体现的是"你怎么验证功能真的生效"，而不是"你写了多少代码"。

### Q33 免构建前端（原生 ESM）的取舍？

**一句话**：收益是零构建、零 node_modules、部署只需静态文件；代价是没有类型检查、没有 HMR。
我们用两个纪律补：① 每个模块 `node --check`（进了 pytest，一个模块语法错会让整页空白，
我们就因为少一个 `)` 白屏过）；② 公共能力收敛到 `api.js`/`ui.js`/`i18n.js`。

**深入**：如果团队更大、页面更多，我会换构建链——这是**场景决定的取舍**，不是信仰。

### Q34 怎么保证"改了不改坏"？

**一句话**：99 项测试分四层：纯逻辑单测（指纹状态机/通知节奏/检测算法）、
服务层测试（诊断报告校验、防护栏、收敛）、集成测试（真实容器 + 真模型跑一次诊断）、
以及**接口矩阵 + 前端资源语法门**。改动的验收流程写进了教程 11。

**深入**：还有一条纪律——**测试要能重复跑**。我们踩过"测试依赖数据库现状"的坑
（`_tick()` 走全局 reconcile，库里有别的规则就会偶发失败），改成只驱动被测规则；
也踩过"跑完不清数据"留下幽灵告警的坑。

### Q35 数据一致性上踩过什么坑？

**一句话**：三处值得说：① 早期用主机名写 `host_ident`（而链路里是 ident）→
对这类事件跑诊断全是"主机未注册"，写了修复脚本 + 单位换算；② 事件关闭后 `source_key`
没释放 → 同源告警再触发会并进已关闭事件（用墓碑键 + 锚点重指修）；③ 压测删主机后
**活跃事件没跟着删** → 100 条幽灵告警挂大盘（补清理 + 运维手册）。

**深入**：共同点是"**主数据变更后，派生数据要跟着变**"。这类问题在"删除"路径上最容易漏。

### Q36 多环境部署踩过什么？

**一句话**：最坑的是 **`.env` 按当前工作目录解析**——从仓库根跑测试读不到 `backend/.env`，
密钥回落成占位值 → 已加密的 api_key 解不开 → 向量召回静默降级。
修法是 `env_file` 锚定到包内路径；容器部署则一律走**环境变量**。

**深入**：另一个环境坑：本机同时存在**原生 seekdb（IPv4:2891）**与 **docker 映射（IPv6:2891）**，
本地测试与容器 API 连的是**两个不同的库**，排查时极易误判（对比
`SELECT MAX(id) FROM audit_logs` 立刻能分辨）。

### Q37 你的数据库迁移策略？

**一句话**：Alembic 管理，但**不用 autogenerate**——SeekDB 的索引反射不可靠
（`BLOCK_SIZE` 语法），所以迁移里的索引都手写，并关掉索引/唯一约束的比对；
VECTOR 列的表登记进 `_NO_REFLECT` 走 raw SQL。每次迁移都在真实库上跑过 `upgrade`/`downgrade`。

### Q38 事件与规则删除了，数据怎么收尾？

**一句话**：规则删除是**软删**（`disabled=true`），但对账会立刻停掉它的 worker；
事件删除走"恢复"语义（删 cur、追加 his）。另外提供 `repair_demo_data.py --purge-orphans`
清理"主机或规则已不存在"的孤儿活跃事件——**这类事件不会自己消失，会一直挂在大盘上**。

## 四、压力与反问（8 题，含"正确的废话"风险）

### Q39 「你们为什么不用 Prometheus + Alertmanager + Grafana，而要自研？」

**一句话**：因为目标用户是"没有运维团队的个人/小团队"，他们的痛点是**30 分钟出效果**
和**出事有人解释**，而不是要一套需要自己拼装的组件。Prometheus 生态强在指标与查询，
但**不给**：一条命令的 Agent 分发、跨类型探活（HTTP/TCP/进程/证书）、
告警的 AI 根因解释、处置闭环与审计。我们做的是**把这条链路串起来**，并且**轨 B 保留 Prom 对接**——
已有 Prometheus 的用户可以把数据源接进来，不是二选一。

**别这么说**："Prometheus 不好"——这会显得你没调研。正确姿势是"边界不同 + 可共存"。

### Q40 「AI 诊断的准确率多少？」

**一句话**：不给准确率数字（**我们对外也不承诺**）。给的是可验证的结构性指标：
报告 schema 合规率、结论档位分布、引用可回放率、人工抽检证据是否支持结论。
我认为**"不知道"是合法结论**——把不确定说清楚，比给一个自信的错根因对运维安全得多。

**深入**：如果面试官追问"那你这个 AI 有什么价值"：价值是**把取证过程自动化**——
8 个工具、十几步查询、把证据整理成带引用和影响面的报告。人做同样的事要 30 分钟，
它 1-3 分钟出草稿，**且每一步可回放**。价值在"省时间 + 可追溯"，不在"替人下判断"。

### Q41 「你这不就是个 Demo 吗？」

**一句话**：我理解这个怀疑。区分标准是"机制是否真的落地 + 有没有真实验证"：
指纹双表状态机、对账调度、入队快照、通知三参数、通知台账、两级静默、预算五件套、
报告强 schema（含校验失败重试与 stub）、护栏四层、copy-on-write 版本化——都有代码和测试；
100 主机压测出的是**真实数字**（评估周期 P95 ~100ms、SSE ~10s）；
诊断是**真模型**跑的，报告能在界面上回放每一步。

**同时我也很清楚它的边界**（这点我会主动说）：广度不够（工具 10 个 vs 夜莺 70+、
技能 8 vs 22）、没有生产环境验证（都是合成数据 + 单机）、
若干契约与文档有偏差。**能说清"哪里不行"比说"哪里都行"更能证明我真做过。**

### Q42 「为什么不用 LangGraph/CrewAI 这类框架？」

**一句话**：V1 的循环就是"ReAct + 终态工具 + 预算五件套"，用 `for` 循环 + asyncio 表达最直观、
最好调试、最好加约束（撤工具/拒绝重复/落盘/压缩都在循环体里几行）。框架的价值在多 Agent 编排、
复杂状态机、跨进程持久化——V1 用不到，引入反而增加调试成本。

**深入**：我留了扩展点：多 Agent 只需在 `diagnose()` 外层加一个编排层，工具面与报告契约不用动。

### Q43 「数据只留 2 小时内存，那"27 分钟前的告警"你能查出根因吗？」

**一句话**：能查，但**只能查到聚合粒度**（1m/5m），且报告里会明确写"明细窗口已过，
本结论基于聚合数据"。如果聚合也不够（比如告警窗口在 7 天外），我会给
`INCONCLUSIVE` + 说明缺什么数据——**不编**。

**深入**：这条也是演示时的加分点：主动说出"我的数据保留策略导致什么查不到"，
比等客户问到再解释强。

### Q44 「你怎么保证 AI 不执行危险操作？」

**一句话**：三层：① 诊断/ChatOps 的工具面**全是只读**（没有执行类工具）；
② 处置层的四层护栏（denylist → 只读放行 → 白名单开关 → HITL 审批），
每次判定（含拒绝）都写 `action_audit`；③ V1 **根本不在目标机执行命令**——
平台只判定 + 审计 + 返回一条可复制的命令给人执行。

**深入**：这个边界必须在销售和演示里讲清楚（不要宣传"无人值守自动处置"）。

### Q45 「如果让你重做，你会改什么？」

**一句话**：三件：① **把能力集做成第一天的设计**（而不是等出现前后端口径不一致的线上问题才补）；
② 热路径一律异步化 + 限并发 + 压力下可放弃（AI 摘要阻塞告警队列那个坑代价很大）；
③ 从第一版就建接口矩阵测试（路由覆盖守卫），而不是靠人记得加。

### Q46 「你的项目最难的技术点是什么？」

**一句话**：不是 AI，是**"让状态机在重启、静默、更新、恢复、删除五种变更下都不出错"**。
具体说：指纹要覆盖"变更即新事件"的语义；MutedAll 要顺手清指纹否则永不重触发；
更新事件必须入队否则重复通知失效；事件关闭要释放锚点否则同源告警并进已关闭事件；
重启要回放且通知计数续算。这些每一条都是独立的、互相牵制的约束——
**你能说出这些约束，就说明你真维护过这个状态机。**

## 五、简历怎么写 / 面试怎么讲

### 5.1 项目描述模板（三行版）

> **AI 运维监控平台**（个人项目，源码产品）
> - 独立设计与实现：内置 Agent 采集（psutil + 探活）、指纹状态机告警引擎（cur/his 双表账本、
>   对账调度、通知节奏三参数）、AI 根因诊断 Agent（ReAct + 8 只读工具 + 报告强 schema 校验 + 三层留痕）、
>   Runbook 处置闭环（四层护栏 + 审计）；
> - FastAPI + SQLAlchemy async + SeekDB（含向量召回）+ 原生 ESM 前端（12 页，免构建）；
> - 99 项自动化测试（含接口矩阵守卫）；容器内压测 100 主机：评估周期 P95 ~100ms、告警 SSE ~10s。

### 5.2 三个"必讲"的故事（都是真事，细节丰富）

1. **告警风暴下通知延迟**：压测发现事件队列积压 1793 条 → 定位到消费端 `await` 了真调 LLM 的
   摘要 → 改后台任务 + 并发上限 + 队深让路 → SSE 延迟从分钟级降到 9.8s。
   **考点**：热路径意识、可观测性（自检端点）、量化改进。
2. **"更新不入队"导致重复通知从未生效**：单测全绿但功能没生效，因为只测了纯函数没测链路。
   **考点**：测试层次的理解、对自己代码的怀疑精神。
3. **前后端权限口径不一致**：演示账号点 AI 助手必然 403 且报错不可读 →
   修成"服务端能力集是唯一来源 + 统一错误信封 + 路由覆盖守卫测试"。
   **考点**：从"修一个 bug"上升到"消除一类问题"。

### 5.3 反问面试官的问题（显得你在做产品而不是写作业）

- 你们的告警量级与"通知延迟"的 SLO 是怎么定的？
- AI 诊断类功能，你们怎么评估质量、怎么处理"AI 说不清"的情况？
- 如果要做多租户，数据可见域是怎么设计的（我们单租户版本刻意没做）？

### 5.4 现场可以打开代码讲的三个点（准备一个能上网的环境）

1. `app/engine/state.py` —— 指纹状态机（**纯逻辑、可单测**，最能体现设计功力）；
2. `app/services/findings.py` —— 报告强 schema 校验与归一化（体现"让 AI 输出可校验"）；
3. `tests/test_d8_api_matrix.py` —— 路由覆盖守卫（体现工程完备性）。

> 最后提醒：**不要背"高并发/千万级"这类与项目规模不符的话**。这个项目的价值是
> "机制正确 + 边界诚实 + 可验证"，把这三件事讲透，比吹规模有说服力。
